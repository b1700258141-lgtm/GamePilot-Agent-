# 关键设计决策

## 2026-10-12：TASK-006G 先做四 seed 胜利目标配对门槛

单格真实 canary 仅验证 seed 2 的死亡后反击缺陷，无法观察其他 seed 的
正常胜利目标是否误报或未完成。先固定连续 seed 0–3，每个 seed 配对
normal 与该缺陷 profile，共八格；这个窄门槛保留四 seed 差异，最多
48 次模型调用，比直接进行 48 格矩阵更容易定位失败。离线测试替身
必须逐格新建，真实供应商配置贯穿八格一致。只在执行错误时止损，
有效漏检和误报继续记录；真实付费执行另行决定。

## 2026-10-12：TASK-006F 将单格手工复核固化为只读命令

真实 seed 2 canary 的五份 JSON 已人工交叉核对，但后续重读或 CI 复核
不能依赖人工判断。固定一个仅接受 TASK-006E 当前单格版本的核验命令，
对摘要、原始游戏事实、重放、同 seed 对照和逐次模型用量交叉核对；
不增加任何模型请求或游戏操作。单格证据可信度与模型跨 seed 泛化能力
是两件事，完整真实矩阵仍须另行定义。

## 2026-10-12：TASK-006E 先用单格 canary 验证真实跨 seed 入口

48 格真实矩阵最多可能产生 288 次供应商调用；在 seed 42 的一次小样本
之外，尚无新 seed 的真实模型运行证据。先固定 seed 2 的死亡后反击胜利格，
它有四次攻击的可达见证，能检查模型在不同胜利路径上的决策。单格配对
仍保留独立规则判定、无模型重放与同 seed 脚本对照。CLI 默认测试替身，
真实模式需显式付费开关；6 次调用和 3,072 输出 Token 是技术上限，
输入用量与金额在缺少可靠单价时不承诺上限。离线成绩与真实能力分开。
后续获授权的一次真实 seed 2 单格以 4 次调用检出目标规则并重放一致；
它只支持该格结论，完整真实矩阵另行定义，验收见
`docs/validation/TASK-006E-agent-seed-canary.md`。

## 2026-10-12：TASK-006D 用预算内可达性定义真实缺陷机会

固定 seed 下的缺陷 profile 不等于可检测缺陷：若所有允许的动作路径都
无法进入缺陷分支，把该格计入真实模型召回分母会误判模型。对 seed 0–3
和三种预定缺陷，在每格 6 次游戏动作预算内穷举两种公开动作；可达格
保存最短见证，并用真实 HTTP 脚本与独立规则检查复核。不可达格保留在
固定计划分母中，但从“可检出机会”分母单独区分，不重写历史 1.0.0 证据。

## 2026-10-12：TASK-006C 先预检四 seed 的 Agent 工程链路

原 Agent 配对评测的脚本对照固定 seed 42，不能仅修改 Agent seed 而继续沿用
该对照：seed 2 的胜利条件需要四次攻击。先冻结连续 seed 0–3 的 48 格
离线清单，按 seed 固定脚本并经 HTTP 独立验证；Agent 动作仅由观测驱动
测试替身选择。统计缺陷实际触发和触发后的规则检出，未触发不算漏检。
此切片验证工作流和证据链，不作为真实模型跨 seed 能力结论。

## 2026-10-12：TASK-006B 将同进程 replay 与跨进程复现分开

TASK-006A 每格的无模型 replay 与原运行共享一个 Python 进程，虽已验证逐字段
确定性，仍不能单独覆盖重新启动后的差异。使用第二个独立进程按同一固定清单
再运行一次，并严格核对报告身份、SHA-256、计数、规则结论与真实游戏轨迹。
输入损坏或缺失归执行/证据错误，不误记为游戏漂移；只有完整有效证据的差异
才归偏差。原始报告和旧 1.0.0 摘要不覆盖，新增 1.1.0 指纹格式供严格对比。
此切片仍不调用模型；Agent 的 seed 42 胜利对照脚本不能直接移用于其他 seed。


## 2026-10-12：TASK-006A 先验证跨种子确定性与规则判定

真实 Agent 的 V6 结论仅来自 seed 42 的固定小样本。为避免把脚本能力误当作
模型泛化，先固定 seed 0–31、两条动作轨迹与四个隔离靶场，使用现有 HTTP
执行器、独立规则判定器和无模型重放。每格同时保留靶场实际触发与规则失败，
两者不相互替代。CI 中运行此离线检查；真实 Agent 跨种子、费用与长期稳定性
须另设预算和验收。TASK-005B 的 `/ready` 同步覆盖独立内存靶场。


## 2026-10-10：TASK-005C 在 CI 中验证真实容器路径

原三项 CI 分别覆盖离线逻辑、独立数据库和安装包，尚未执行应用镜像与
Compose 中的迁移、API、重启持久化链路。增加第四个独立任务，
在临时 runner 构建镜像并运行既有 `gamepilot.testing` 和 `container_smoke.py`。
专用项目和回环端口避免与其他任务共享状态；失败时上传已有报告和服务日志。
本轮不推送、不配置远程分支保护，也不将本机结果称为 Linux runner 成功。

## 2026-10-10：TASK-005B 区分存活与就绪

第五阶段容器已能持久化和恢复，但原 `/health` 仅检查 HTTP 进程，
运行中数据库断开时容器仍会被视为健康。新增 `/ready` 执行只读连接探测，
并让 Docker 健康检查使用它；`/health` 保持原有存活语义。
内存后端与显式注入仓储不由应用猜测外部依赖。
就绪失败沿用 `persistence_unavailable` 的 503 安全响应，不记录原始连接异常。
启动探测、迁移顺序、游戏接口和数据库结构不变。

## 2026-10-10：TASK-005A 独立本地容器交付

第四阶段闭环与 CI 配置已有可验证产物，下一步落实既定 Docker 交付目标。
新增独立 Compose 文件，避免更换或复用现有开发数据库卷；暂不公开服务。
数据库健康后运行显式的一次性迁移服务，只有迁移成功才启动 API，
保持“应用本身不自动迁移”的既有边界。

应用镜像采用多阶段基础 wheel 安装、非 root、单 worker。上下文使用白名单，
避免把本机环境文件与历史证据发送给镜像构建器。健康检查沿用 HTTP 存活接口，
不将它宣称为持续数据库就绪检查。容器交付不增加模型调用或改变游戏规则。

## 2026-10-09：TASK-004D 回归结果变化与证据核验

新增离线比较能力，复用现有批量报告而不提前引入缺陷状态库。
两份清单须有相同指纹集合和回归规格，按指纹对应而不是按行号对应。
读取时核对清单哈希、单项运行证据、错误后的跳过顺序和汇总数字；
单项分类与在线 `verify_defect` 共用函数。保留输入报告路径与哈希作为对比来源。

`now_passing` 仅表示固定回归项由失败转为通过。其他规则失败也保留原 outcome，
不能将多个受影响回归项的改善等同于修复多个独立缺陷。
任何一侧执行错误、跳过或目标未检查均为不可判定，退出 2；
可比较但仍失败退出 1，全通过退出 0。比较不声称因果关系，不自动关闭缺陷。

## 2026-10-09：TASK-004B 显式清单与批量回归

背景：单项回归已能复现或排除已知规则失败；要反复检查多项缺陷，
需要固定输入分母和统一退出语义。由所有者已授权的 Codex 暂代开发实施。

- 清单只引用同目录内的相对缺陷产物路径与预期稳定指纹。所有产物在发出 HTTP 请求前
  逐项读取和核验；拒绝重复项、越界路径和不受支持的版本，避免半套清单被误认为完整回归。
- 批量层不另写规则判定，逐项复用 `verify_defect`，在目标服务中各开新会话。
  普通规则失败继续执行；执行与证据写入错误优先退出 2 并跳过剩余项。
- 摘要固定计划、执行和跳过数，逐项关联既有运行报告，排他写入以保留历史证据。
  本切片不引入数据库、真实模型调用、并发或自动重试。

影响：`gamepilot.defects batch` 增加显式回归门禁；游戏接口和原报告契约不变。

## 2026-10-08：TASK-004A 缺陷证据到回归规格

背景：第三阶段的 Agent 已能发现并重跑规则失败，但缺少可交给开发者复现、
并在修复后再次运行的独立缺陷产物。所有者授权 Codex 暂代 Claude Code 实施首个闭环切片。

- 输入以 `testing.RunReport` 的游戏事实为准，并要求对应的无模型 `ReplayReport`
  在目标场景逐字段 match；可选 Agent 报告只用于核对关联和错误优先级，
  不把模型自述当成缺陷判定。
- 同一失败步骤可能触发多条规则，导出时允许从已失败的游戏规则中选定目标规则。
  回归动作仅取已执行前缀；稳定指纹由规则版本、规则 ID、seed 与动作前缀计算，
  不依赖随机 run_id 或本地文件路径。
- 一份缺陷 JSON 同时保存可读缺陷单和 `Scenario` 回归规格，避免多文件部分写入。
  `verify` 使用调用时提供的目标地址与既有 `GameClient`/独立判定器；目标规则未被执行
  也不能记作修复通过。
- 此切片不新增数据库表、外部 Issue 集成、模型调用或自动修复。
  缺陷生命周期持久化与跨种子评测在首条闭环验收后单独设计。

影响：新增 `gamepilot.defects` 的离线导出与无模型验证命令，
`gamepilot.testing.replay` 增加严格重跑报告读取；既有游戏 API 与报告 schema 不变。

## 2026-09-20：TASK-003B 缺陷靶场与评测口径

背景：执行器已能判定规则是否符合，但「判定器能不能发现缺陷」还没有证据。TASK-003B 需要植入
可控缺陷并给出可复算的评测口径，同时不得改动正常战斗规则、公开 API、仓储与数据库结构。
以下决策在实施中确认。

- 缺陷必须是**真实状态变异**，不是改写 HTTP 响应：三个缺陷都通过领域层的窄扩展点实现
  （治疗量、药水扣减、是否反击），生命值、药水数量与事件历史都真的被改动，客户端看到的是
  与正常实现同一条路由、同一份响应 schema 的真实结果。响应注入只允许用于执行器异常路径测试。
- 接入面选择「三个扩展点 + 路由会话工厂注入」，而不是复制战斗引擎或加运行期开关：
  `CombatSession` 的默认实现就是原有行为（`normal` profile 与正常实现逐字段一致），
  缺陷以子类覆盖三个钩子；路由用 `Depends` 取会话工厂，正常应用仍绑定默认工厂。
- 靶场是独立内存入口：`gamepilot.lab` 不导入 `main.py`、不读 `.env`/Settings、只使用内存仓储，
  即使 `REPOSITORY_BACKEND=postgres` 也不创建数据库 Engine；非法 profile 明确报错，
  不静默退回 normal。profile 由启动参数决定，游戏 API 上不存在读取或切换它的入口。
- 触发记录与缺陷检出是两件事：靶场按 `session_id + fault_id` 记录**首次真实偏离**
  （缺失生命值恰好等于治疗量时不记录，因为那种情况下行为与正常实现完全一致）；
  判定器仍然只看 HTTP 观测，不读缺陷标签或标准答案，目标规则只用于评测摘要核对。
- 评测矩阵先于运行写死在 `manifest.py` 并带版本号：4 个 profile × 8 个基线场景 = 32 个组合，
  预期 9 个 fail / 23 个 pass。清单是标准答案，不得在结果不符时反向修改。
- 同 profile 各重跑一次（32 次，走既有 `replay`），另加 1 次负向验证：缺陷轨迹在 `normal` 上重放
  必须 `mismatch`，否则说明比对器分辨不出缺陷。该次不计入 32 次重跑。
- 指标分母一律来自固定清单而不是实际跑到的组合数：执行错误单独计数并从「发现缺陷」里排除，
  「没跑到」不会让分母变小；同一缺陷命中多条规则只计一次发现。
- 退出码与执行器分离：`0` = 32 个组合全部符合清单（含成功发现预植入缺陷，这是预期结果）；
  `1` = 漏检/误报/触发不符/重跑差异；`2` = 输入、执行或报告 I/O 错误，且优先于 `1`。
  评测自己跑不出结论时绝不返回 `0`。
- 评测在进程内用真实 FastAPI + ASGITransport 顺序执行，报告里的地址是占位地址
  （`benchmark.invalid`），不声称使用真实网络；真实 localhost HTTP 验证由
  `gamepilot.lab serve` + `gamepilot.testing run/replay` 手动完成，两者不可互相替代。
- 所有报告排他创建、保留旧产物，不自动清理会话、开发库或磁盘目录。

影响：领域层新增三个可覆盖钩子并在路由引入可注入会话工厂，因此 TASK-003B 要求重跑真实
PostgreSQL 回归（已执行，29 项通过）。本任务不新增数据库表、迁移、并发评测或运行期缺陷开关。

## 2026-09-17：TASK-002B 数据库接入边界

背景：TASK-002A 已验收；现有仓储协议为 save/get，领域对象可通过构造函数和公开动作重放。以下决策细化第二阶段既定路线，实施要求见 TASK-002B。

- 默认使用内存仓储，REPOSITORY_BACKEND=postgres 显式选择 PostgreSQL，注入仓储优先。
- 相同 seed 重放玩家动作恢复状态和随机数进度，再比较完整事件与状态，不使用 Pickle 或私有字段赋值。
- 每次 save 共用事务写入状态与新事件，以状态行锁及事件前缀校验防止过期/分叉历史静默覆盖。部署仍以单写入方顺序操作为边界，不提供分布式请求幂等。
- 现有 API seed 支持超 BIGINT 整数。新增迁移把列由 BIGINT 改为 Text，存规范十进制文本，领域/API 仍为 int。种子不参与数据库数值计算；相比收窄 API 或有限精度 Numeric，这更符合用途。回退 BIGINT 遇越界值必须失败并保留数据。
- 使用独立 TEST_DATABASE_URL 和专用测试库；数据库故障及数据不一致必须明确报错，不能回退内存或自动修复历史。

影响：调整 Settings 条件必填校验、ORM seed 映射，新增 0002 迁移及 PostgreSQL 集成测试。已应用的 0001 不变；规则升级与历史存档版本兼容留待独立设计。
