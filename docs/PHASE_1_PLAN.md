# 第一阶段工作方案：确定性游戏测试靶场

## 1. 阶段目标

第一阶段只完成一件事：建立一个**可重复、可测试、可通过 API 操作的最小回合制战斗系统**，作为后续游戏测试 Agent 的第一个被测对象。

本阶段不接入大模型。原因是 Agent 的操作对象、状态边界和正确结果必须先稳定下来，否则后续无法判断 Agent 是发现了游戏缺陷，还是被测系统本身没有清晰规则。

阶段完成后，应能通过 FastAPI 创建一场战斗、观察状态、执行攻击或使用药水，并通过自动化测试证明相同随机种子和相同动作序列会得到相同结果。

## 2. 本阶段交付物

- 一个可启动的 FastAPI 服务；
- 一个独立于 Web 框架的回合制战斗领域模型；
- 创建战斗、查询状态、执行动作和健康检查 API；
- 支持固定随机种子的确定性战斗；
- 内存仓储及可替换的仓储接口；
- 完整的单元测试和 API 测试；
- 最小 README、项目配置和忽略文件；
- 清晰、稳定的结构化战斗事件，为后续 Agent 观察与缺陷报告提供输入。

## 3. 明确不做

以下内容不属于第一阶段，不应提前实现：

- LangChain、LangGraph 或任何 LLM 调用；
- MCP Server 或 Skills；
- PostgreSQL、Redis 或其他数据库；
- Docker、Docker Compose 或线上部署；
- 网页前端、Playwright 或视觉识别；
- 多 Agent 编排；
- RAG、游戏设计文档解析或向量检索；
- 商店、背包、任务、奖励、装备和存档；
- 登录、权限、用户体系；
- 故意植入 Bug 的管理系统；
- 微服务拆分和消息队列。

这些能力将在被测核心稳定之后按阶段加入。

## 4. 技术栈

### 运行时与应用

- Python 3.12+；当前本地解释器为 Python 3.14.6，实施时需要验证依赖兼容性；
- FastAPI：HTTP API；
- Pydantic v2：请求、响应和配置的数据校验；
- Uvicorn：本地 ASGI 服务。

### 测试与质量

- Pytest：领域逻辑与 API 测试；
- HTTPX：FastAPI 接口测试；
- Ruff：代码检查和格式化；
- 标准库类型注解：保持核心接口明确。

### 暂存储

- 第一阶段使用进程内内存仓储；
- 领域服务只依赖仓储抽象，不直接依赖全局字典；
- 第二阶段再将实现替换为 PostgreSQL，以便学习表设计、事务和迁移。

## 5. 最小游戏规则

游戏只有玩家与史莱姆的一场回合制战斗。

初始状态：

- 玩家最大生命值和当前生命值均为 100；
- 玩家拥有 2 瓶药水；
- 玩家攻击伤害为 18～25；
- 史莱姆最大生命值和当前生命值均为 60；
- 史莱姆攻击伤害为 20～35，使 `lost` 分支可由公开动作真实触发；
- 战斗状态为 `active`，回合数为 0。

允许的动作：

- `attack`：玩家攻击；如果史莱姆仍存活，史莱姆立即反击；
- `use_potion`：玩家恢复 25 点生命但不能超过上限，消耗 1 瓶药水，随后史莱姆反击。

状态规则：

- 生命值最低为 0；
- 史莱姆生命值降至 0 时状态变为 `won`，且不再反击；
- 玩家生命值降至 0 时状态变为 `lost`；
- 每个成功执行的玩家动作使回合数加 1；
- 战斗结束后不允许继续操作；
- 没有药水或玩家满血时使用药水视为无效动作，不得修改状态；
- 无效动作返回明确的领域错误，并由 API 映射为 HTTP 409；
- 未找到战斗会话返回 HTTP 404。

## 6. API 边界

第一阶段只提供以下接口：

```text
GET  /health
POST /api/v1/game-sessions
GET  /api/v1/game-sessions/{session_id}
POST /api/v1/game-sessions/{session_id}/actions
```

创建战斗请求允许传入整数随机种子。动作请求只接受 `attack` 或 `use_potion`。

所有游戏接口返回结构化快照，至少包含：

- `session_id`
- `seed`
- `status`
- `turn`
- 玩家状态
- 史莱姆状态
- 结构化事件历史

事件中应能看出谁执行了什么动作、产生多少伤害或治疗，以及动作后的关键状态。第一阶段不保存自由文本形式的 Agent 推理。

## 8. 验收标准

第一阶段通过需要同时满足：

1. 服务能在本地启动，`/docs` 可访问；
2. API 能完成创建、观察和执行战斗动作的闭环；
3. 领域逻辑不依赖 FastAPI，可直接通过单元测试调用；
4. 相同随机种子和相同动作序列产生相同的战斗事件和最终状态；
5. 关键非法状态具有明确错误，而不是静默失败或返回 HTTP 500；
6. 所有测试通过；
7. Ruff 检查通过；
8. README 包含安装、启动、测试和最小调用示例；
9. 没有提前引入本阶段明确排除的组件；
10. Codex 完成独立代码审查后才视为阶段完成。

## 9. 本阶段学习目标

项目所有者应在本阶段理解：

- FastAPI 路由、依赖和 Pydantic Schema 的职责；
- 领域模型为什么要与 API 层分离；
- 状态机、合法状态转换和领域不变量；
- 随机种子为什么对游戏测试回放重要；
- 单元测试和 API 集成测试的区别；
- 仓储抽象为什么能帮助下一阶段接入数据库。

## 10. 完成后的下一步

本阶段验收通过后，再规划第二阶段。当前倾向是引入 PostgreSQL、SQLAlchemy 和 Alembic，将内存战斗记录替换为持久化实现，并首次加入 Docker Compose；最终范围以阶段复盘后的决策为准。
