# 第四阶段：把已确认缺陷沉淀为回归用例

状态：2026-10-09 TASK-004A 至 TASK-004D 已实施；TASK-004E 持续集成配置和本机验收完成，
远程工作流运行待所有者后续授权推送。
首两切片的原详细验收已归档，索引见 `docs/validation/ARCHIVED_REPORTS.md`。

## 背景与目标

第三阶段已有确定性测试执行器、独立规则判定器、可控缺陷靶场和单 Agent；
V6 真实模型固定 12 格小样本检出三处预定缺陷，原始运行与无模型重跑报告均保留。
此前项目尚不能从一份已确认的规则失败报告直接产出可读缺陷单和可再次执行的回归用例。
因此先补齐「发现 → 证据 → 回归」闭环，不继续扩大模型能力或付费样本。

本阶段的第一项交付是 TASK-004A：从现有报告中离线导出缺陷单和**到首个失败为止的实际执行前缀**，
然后用现有 HTTP 客户端与判定器在新会话中验证该用例。缺陷仍由确定性规则确认；
模型只负责选动作，不能自行宣称规则已违反。

## 首个可验收切片

1. 只接受与原运行匹配的无模型重跑证据、明确的规则失败以及完整动作轨迹。
   执行错误、预算中断、未比较重跑和单纯目标未达成都不得生成「已确认缺陷」。
2. 生成一份结构化缺陷单，指向原始报告并包含规则、步骤、期望/实际、seed、动作前缀、
   复现说明与证据引用。报告不复制凭据、模型原文或整份 HTTP 响应。
3. 生成一份回归规格：相同 seed 和实际动作前缀，在新会话运行已有独立判定器。
   修复后的正常靶场应通过；相应的缺陷靶场应在目标规则上失败。
4. 三个已知缺陷各形成一条回归规格，重复导出相同规则与轨迹能够识别为同一逻辑缺陷；
   任一输入或报告写入错误明确失败，已有产物不得覆盖。

TASK-004A 详细范围与验收见 `docs/claude-tasks/TASK-004A-defect-regression-artifact.md`。
草案形成时，现有非 PostgreSQL 回归为 485 passed、29 deselected，Ruff 检查与格式检查通过；
这只是实施前基线，不是 TASK-004A 的验收结果。

## 第二切片：固定回归清单

TASK-004B 将多份已确认缺陷产物放入显式清单；在执行前检查全部路径、指纹与规格，
再顺序复用 TASK-004A 的无模型验证。批量摘要保留固定计划分母、逐项结果、
执行错误后的跳过项及每项运行报告引用。规则失败继续，执行或写入错误停止。
它为修复后的回归门禁提供可复现的输入和输出，不据此推断跨 seed 稳定性。
详细范围见 `docs/claude-tasks/TASK-004B-batch-regression.md`。

说明见 `docs/CI.md`，验收见 `docs/validation/ARCHIVED_REPORTS.md`。

单项运行证据及固定分母，按指纹对应修复前后结果。错误或跳过不视为修复成功；
规格集合改变则拒绝比较。不新增自动关闭缺陷、数据库或外部发布行为。
验收见 `docs/validation/ARCHIVED_REPORTS.md`。

TASK-004C 新增 `gamepilot.defects demo`：在新环境现场生成三种脚本缺陷的确认链，
导出清单并验证正常及三个缺陷靶场。每次使用独立目录；不依赖本机 V6 历史报告，
不调用模型，明确标识 `offline-scripted-asgi`。任务与验收分别见
`docs/claude-tasks/TASK-004C-reproducible-demo.md` 和
`docs/validation/ARCHIVED_REPORTS.md`。

先复用 `gamepilot.testing` 的 `RunReport`、`ReplayReport`、`Scenario` 和判定器，
不重写游戏规则，不让缺陷标签进入 Agent 决策输入，不调用真实模型。
暂不建缺陷数据库、GitHub Issue 集成、自动提交、自动修复、跨种子稳定性结论或新 UI。
持久化缺陷生命周期和更大样本评测应在首条闭环验收后另行设计。

阶段完成的条件不仅是生成文件，还包括：从报告安全导出、在缺陷版本上复现规则失败、
在正常版本上通过、错误路径不误报以及操作者能够根据缺陷单独立重现。
