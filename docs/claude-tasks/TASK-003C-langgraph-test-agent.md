## 1. 背景与目标

TASK-003A 已提供 HTTP 工具、独立规则判定、证据报告和动作重跑；TASK-003B 与 R1
已验证三个真实缺陷、32 个脚本组合，以及执行错误优先退出 2 的约定。
现有成绩证明的是固定脚本能力，尚无模型自主选择动作的证据。

本任务只完成一条闭环：

> 接收测试目标和规则 → 创建会话 → 模型根据当前观测选择动作 → 执行并确定性校验
> → 根据新观测继续或停止 → 保存报告 → 不调用模型重跑实际动作。

例如给出“验证受伤后的治疗与资源变化”，Agent 自行决定如何受伤、何时喝药。
程序根据真实事件确认是否违规，并保存可重跑轨迹。战斗获胜不等于测试任务完成。

## 3. 推荐路线与范围

推荐 **LangGraph + 现有 Python HTTP 工具适配器**，暂不先做 MCP。
LangGraph 负责显式状态与分支，后续 MCP 负责向其他客户端开放稳定工具，两者职责不同。
这一步集中学习“模型决策、确定性执行、状态推进、失败终止”，减少同时引入协议层的排错成本。

本次包含：一个 Agent、一个模型适配器、串行工具调用、内存工作流状态、预算控制、
离线可测的模型替身、JSON 报告、无模型轨迹重跑和小规模对照评测。

本次不包含：MCP、RAG、多 Agent、前端、视觉测试、任意代码执行、数据库工具、
新数据库表、LangGraph 持久化检查点、跨进程续跑、应用容器化和外部发布。
不增加修复游戏缺陷或自动修改测试判定规则的能力。

## 4. 工作流与工具边界

推荐节点：`initialize → decide → validate → execute → check → route`，
`route` 返回 `decide` 或进入 `finalize`；任何错误、超限和取消都收口到报告保存。
使用 LangGraph 的显式图和条件边，不用隐藏内部循环的通用 Agent 封装掩盖预算与错误状态。

工作流状态至少保存：任务与 seed、会话 ID、最新快照、决策记录、已尝试动作、规则结果、
动作/模型计数、耗时、Token 用量、停止原因和证据路径。状态只保留本轮任务数据。

模型的结构化工具选择仅允许：

- `perform_action(action)`：`attack` 或 `use_potion`。
- `finish(summary)`：申请结束；summary 只是说明，不是判定事实。

创建会话、初始 GET、409 后验证 GET、规则校验和报告写入均由确定性节点管理。
session_id、URL、请求方法、seed、输出路径不由模型提供。每轮最多接受一个工具调用，
禁止并行执行动作；未知工具、多工具请求、非法参数或空响应不得触发游戏请求。
模型适配器需保留 tool_call_id 与对应工具结果关联，以符合所选供应商的协议要求。

模型可见：固定公开规则、自然语言目标、最新公开快照、动作结果、简短规则检查反馈和剩余预算。
模型不可见：profile/fault_id、lab recorder、benchmark manifest、脚本步骤、标准触发轨迹、
评测预期和历史评测答案。也不向模型开放读取源码、文件、环境变量或 shell 的工具。
规则提示词单独维护版本，不直接把包含 seed 提示和触发轨迹的整个仓库文档塞给模型。
保存每轮实际发给模型的脱敏输入以便检查是否泄漏答案；不要求或保存隐藏思维链。

## 5. 增量执行与既有报告兼容

在 `gamepilot.testing` 内提取最小的共享执行能力：开始会话、执行一步并校验、结束并产出证据。
脚本 runner 和 Agent 共同复用；不复制一套 HTTP/409/规则检查逻辑，不导入领域实现。
先以既有测试和固定矩阵证明提取没有改变行为，再接上 LangGraph。
不得为了此任务重写整个执行器或放宽已有报告读取校验。

Agent 只选择动作；该动作的 `expected_status/expected_code` 在请求之前由独立公开规则和
当前已验证快照确定。战斗结束、药水不足、满血等 409 的优先级应查明现有 API 契约，
写入测试，不能由模型填写或根据服务实际返回值反推“预期”。
409 后仍必须 GET 验证状态和事件未变；失败请求也保留步骤骨架和已有观测。

动态生成的每个动作在发送之前追加到本次 `Scenario.steps`，最终按实际选择顺序保存。
仅记录真实选择及尝试，不预填标准脚本；模型主动结束与规则失败早停的完成标志需保持自洽。
不强加固定脚本的 `expected_final_status`；目标覆盖单独记录，不伪造游戏终态要求。

Agent 产物包含：

1. 原有 schema=1.1 的 `RunReport`：保存游戏事实与确定性检查，可由既有 testing replay 读取。
2. 独立版本的 `AgentRunReport`：保存目标覆盖、模型决策、预算、停止原因及 RunReport 引用。

两者以 run_id 关联。预算耗尽或模型失败时，已经成功执行的游戏前缀可以保持其真实规则结果，
但 Agent 任务必须标记未完成或执行错误，不能用前缀 pass 冒充任务通过。
未创建会话就失败时只写 Agent 错误报告，不伪造可重跑的 RunReport。

重跑显式指定目标地址，只读取已执行动作并复用既有 replay；不再次请求模型。
其证明的是游戏轨迹可复现，不保证模型下次生成相同计划。

## 6. 预算、失败处理与退出码

以下为待确认的保守默认值，运行前可显式收紧；配置必须校验为有效正值。

| 项目 | 建议默认值 | 计数与边界 |
| --- | --- | --- |
| 单任务会话 | 1 | 无自动重开、无后台额外探索会话 |
| 游戏动作尝试 | 10 | 成功、409、超时均计数；不得超过 testing 既有上限 20 |
| 模型调用 | 12 | 错误响应、格式纠正也计入；调用前检查剩余额度 |
| 格式纠正 | 最多 2 次 | 全任务累计；重新请求模型，禁止悄悄代填动作 |
| 单次模型超时 | 30 秒 | 超时终止，不自动重试网络请求 |
| 单次游戏 HTTP 超时 | 5 秒 | 沿用既有分类；写动作不重试 |
| 整个 Agent 任务 | 120 秒 | 包含初始化、模型与工具；请求超时取剩余时间与单次上限的较小值 |
| 单次模型输出 | 512 Token | 以选定供应商实际支持的字段生效，记录配置 |
| 付费运行 | 默认关闭 | 必须显式选择真实模型并配置预算，普通测试与 fake 模式不联网 |

禁用 SDK 隐式重试，避免应用计数与实际请求数不一致。LangGraph recursion limit 仅作为兜底，
不能替代动作、调用和时间预算。超限后不得再发模型或游戏请求；保存已有证据不受此禁止影响。
动作请求超时可能已经生效，记为执行错误并停止，不能假定未执行或自动再发一次。

模型已确定为 DeepSeek `deepseek-v4-flash`，单批费用上限与计价币种待确认。
真实调用前按输入与最大输出预估费用，
给下一次调用预留额度；费率、用量来源与估算方法写入报告。缺少可靠计价或 Token 上界时，
不得声称有严格金额上限，应在选型时明确采用供应商额度控制或仅接受调用/Token 上限。
usage 不可用时记 unknown，不记 0；真实运行预估超支立即停止，不自动换模型或追加批次。

Agent `run` 建议退出语义：

- `0`：覆盖目标已达到，所观察规则均通过，正常完成。
- `1`：已有独立规则证据确认游戏违规。
- `2`：模型/工具/输入/报告错误，任一实际执行错误优先于其他结论。
- `3`：正常请求但目标未完成，例如提前 finish、动作预算耗尽或走到不适合目标的终态。

退出 3 为新 Agent CLI 的独立语义，不改变 testing/benchmark 的 0/1/2 契约。
规则失败立即保存和停止；服务错误不计缺陷，模型声称“发现 Bug”不计缺陷。
若使用完整评测 CLI，应另按评测是否达标决定其退出码，并在帮助文本写明两者区别。

## 7. 最小评测：12 组合配对试验

保留原 003B 的 32 组合及七项指标，作为确定性回归，不重命名为 Agent 成绩。
首次 Agent 评测从其中选择三个目标；4 profiles × 3 目标 = 12 组合。
这是一套明确标注的子集试验，不声称已经完成全部 32 组合的 Agent 对照。
目标仅描述要验证的行为，不包含动作顺序。全部使用既有对应场景的 seed=42。

| 对外目标 ID | 给 Agent 的测试目标 | 仅评测层使用的脚本对照 |
| --- | --- | --- |
| full-health | 验证满血时使用药水的处理及状态是否保持一致 | potion-at-full-hp-rejected |
| healing | 验证受伤后的治疗边界及药水资源变化 | attack-then-potion |
| victory | 验证击败敌人的回合及战斗结束后的操作限制 | win-then-rejected |

目标完成采用确定性覆盖条件：full-health 必须观察到满血喝药的预期拒绝且 GET 不变；
healing 必须在受伤快照下尝试喝药，并完成对应事件/状态校验；victory 必须观察到获胜回合，
随后验证终态动作被拒且状态不变。单纯 finish 或耗尽动作不满足覆盖。
已确认规则失败可提前停止；“发现缺陷”和“覆盖目标”仍分别记录。

对照组用原三个 Scenario，实验组使用 Agent。两组使用相同 seed、profile、新会话、
动作上限和 oracle；报告分别记录实际动作数与耗时，不假称脚本也消耗了模型预算。
相同 profile 的模型输入不得包含不同提示或标识；评测进程在模型上下文之外选用靶场。
Agent 模块不得导入 lab/benchmark/scenarios；独立评测模块可以组装它们。

脚本子集的固定预期：healing 在两个药水变体上失败，victory 在死亡后反击变体上失败，
其余九格通过。Agent 路径不同，不直接套用脚本 pass/fail 表作为实际触发事实。
评测层结合 recorder 和目标 rule_id 确认真实触发及命中，不能只根据 profile 认定检出。

摘要至少包含：

- 预定三个缺陷机会检出数 / 3：两个 healing 格及一个 victory 格；未到达和执行错误不缩小分母。
- 去重缺陷覆盖 / 3；其他目标意外发现的缺陷单列，不补填未完成的预定机会。
- normal 误报 / 3；变体未触发时的误报按实际未触发格数另列，分母为 0 时标记 N/A。
- 目标覆盖 / 12、未完成 / 12、执行错误 / 12，保留逐格结果，不能只列成功样本。
- 每格动作数、模型调用数、Token、耗时与费用；unknown 不参与伪造总费用。
- 同 profile 无模型重跑：12 个计划格逐一记录 match/mismatch/not_comparable/未执行，
  报告 match/12 及可比较数，不通过排除失败样本提高成功率。

工程门槛与模型效果分开验收：离线替身应通过所有控制和异常路径测试；真实模型的首轮
12 格演示建议达到预定机会 3/3、normal 误报 0/3、执行错误 0/12，并如实列出目标覆盖。
未达到时保留失败报告，不能换提示重跑后只展示最好一轮。当前只是小样本冒烟，
不据此宣称泛化或优于脚本；多次重复与新 seed 的泛化评测留到后续任务。

## 9. 必须验证的行为

1. fake provider + 真实 ASGI lab 完成创建、逐步决策、执行、判定和报告；模型后续输入确实包含
   上一步观测，改变观测会改变测试替身的下一步选择，不能仅执行预生成的完整脚本。
2. 三个缺陷均可由受控动作触发，产出原有规则证据；normal 无误报。
3. 未知工具、非法动作、多工具调用、空输出、连续格式错误不产生未授权游戏请求；
   格式纠正耗尽、finish 太早、循环攻击、达到预算均有明确终止与报告。
4. 模型超时、拒绝响应、429/5xx、游戏超时/503、409 后 GET 失败均正确分类；
   通过真实 CLI 验证退出码、计数、部分证据落盘及错误优先，而非只测辅助函数。
5. 预算在调用前检查；SDK 无隐式重试；计数不能被重新进入节点重置；
   使用可控时钟测试临近总时限，不用长时间 sleep。
6. 动态 RunReport 通过原有严格读取与 replay；所有实际动作原样重跑、没有额外模型调用。
   包括正常完成、规则失败早停、预算终止前缀与执行错误的 not_comparable。
7. 对至少一条缺陷轨迹，在 normal 重跑应 mismatch；重跑错误不能降级为 mismatch。
8. 检查导入边界和实际模型输入，确认没有 profile、答案、脚本轨迹或凭据；
   工具响应中的指令性文本不能扩展工具白名单或改变 URL/预算。
9. 原测试、Ruff 和原 32 组合 benchmark 通过；旧报告契约及规则不变。
